# 选型与速查

前面十篇讲原理。这一篇只做两件事：按场景给你答案，以及列出一批真实会出事的反模式。

## 按场景查

### 你要给人做登录

| 场景 | 选择 | 理由 |
|---|---|---|
| 普通 web 应用 | session cookie + 强哈希 + TOTP 可选 | 最简单、可撤销、够用 |
| 想抗钓鱼 | 加 passkey | 唯一同时抗钓鱼且可用的方案 |
| 移动 app | passkey + refresh token | 别在 app 里存 client_secret |
| 企业客户要 SSO | SAML + OIDC 都做 | 客户只会支持其中一种，你得全有 |
| 有高价值操作（转账/改邮箱） | 加 step-up 认证 | 登录被攻破时还有第二道门 |

### 你要给程序做认证

| 场景 | 选择 | 理由 |
|---|---|---|
| CI 访问云 | OIDC 联邦 | 消灭长期密钥，零成本 |
| 云上服务访问云资源 | 实例角色 / managed identity | 不需要任何配置 |
| k8s 内服务间 | SPIFFE 或 service mesh mTLS | 身份由平台分配 |
| 跨边界、对方不支持 OIDC | 短期 token + token exchange | 别用长期 key |
| 确实只能放静态凭据 | secret manager + 强制轮换 | 加审计，加过期 |
| 个人脚本调 GitHub | 细粒度 PAT + 设过期 | 尽量换成 fine-grained |

### 你要管服务器

| 场景 | 选择 |
|---|---|
| 登 Linux | SSH key（私钥带口令 + agent） |
| 登录一大批机器 | SSH 证书（CA 签发），别手工登记公钥 |
| 需要硬件保护 | 密钥放 YubiKey 的 PIV 槽 |
| 签 git 提交 | SSH key 签名（Git 2.34+）或 GPG |
| 传文件 | 别开 agent forwarding，用 ProxyJump |

### 你要存东西

| 存什么 | 放哪 |
|---|---|
| 人用的密码 | 密码管理器（云同步，端到端加密） |
| 人用的 passkey | 平台钥匙串或密码管理器（接受同步） |
| 最高价值的 passkey | 硬件密钥，买两根 |
| 开发者的 SSH key | `~/.ssh`，600 权限，带口令 |
| 服务端的密钥 | KMS / Vault，绝不在配置文件 |
| 少量必须离线的东西 | 纸质恢复码 + 物理保险 |

## 十条规则

1. **优先消灭凭据，而不是保护好凭据。** 不需要存在的东西最难泄露。能用短期签发的地方不要用长期 key。
2. **凭据的寿命由泄露窗口决定，不是由方便决定。** 一个能存活一年的 token，等于一年的暴露期。
3. **对称凭据必须能撤销，非对称凭据必须能删除。** 做不到其中之一的方案，别上生产。
4. **恢复路径的安全等级，就是你的安全等级。** 加固主路径而不加固恢复，等于没做。
5. **抗钓鱼需要把目标编码进凭据。** TOTP 做不到，passkey 做到了。这是唯一一个"换方案就换安全等级"的地方。
6. **多因素要求类别不同，而且不能同时失守。** "密码 + 安全问题"不是 MFA。
7. **私钥在哪儿，安全等级就在哪儿。** 文件 < agent 内存 < TPM < 不可导出的硬件。
8. **一份凭据一个用途。** 一把 key 走天下，出问题时撤销范围不可控。
9. **假设数据库会泄露。** 这决定了你必须用慢哈希，必须加密敏感字段。
10. **要有"能看见并撤销"的界面。** 用户自救是入侵后的最后一道防线，没有它，泄露之后无从制止。

## 反模式

按危害排：

**一、把"多一步"叫成 MFA。** 密码 + 安全问题、密码 + 邮箱验证码。这两者在攻击者视角下都是单因素。

**二、JWT 当会话用。** 有效期 7 天、无法撤销。泄露后七天内有完全访问权，且你无从干预。

**三、恢复流程用短信。** 主路径是 passkey，恢复靠短信——那实际安全等级就是短信。

**四、token 写进配置文件并提交。** 这是最古老也最常见的事故来源。`.gitignore` 不是安全措施。

**五、agent forwarding 图省事。** 把私钥的签名能力借给了远端机器的所有进程。

**六、"记住这台设备"设成永久。** 30 天里你只有单因素，而且用户不会记得自己开过这个。

**七、scope 给全。** 一个只需要读仓库的 token 给了写权限，泄露后的损失扩大一个数量级。

**八、不分清楚认证和授权。** 把"token 有效"当成"这是本人"。这是 OAuth 历史上最贵的一类漏洞。

**九、只做登录不做撤销。** 没有活跃会话列表，用户被入侵后无法自救。

**十、相信"内网所以安全"。** 零信任的出发点就是这条不成立。

## 一张判定卡

遇到任何一个陌生的凭据或方案，按顺序问：

```
1. 材料：验证方有你的秘密副本吗？
   ├─ 有 → 对称。看撤销和存储。
   └─ 没有 → 非对称。看私钥在哪儿。

2. 出示：网络上传的是什么？
   ├─ 秘密本身 → bearer，截获即可用
   ├─ 一次签名 → 看签的东西里有没有绑定目标
   └─ 派生值 → 看是否一次性、窗口多长

3. 主体：人 / 设备 / 进程？
   └─ 决定能用哪些加固手段

4. 存放：谁能替你用它？
   └─ 决定了实际安全等级（可能远低于理论值）

5. 生命周期：怎么轮换、怎么撤销、丢了怎么办？
   └─ 决定泄露之后的损失上限
```

五个问题答完，你对这个东西的理解已经超过大部分文档了。

## 最后

这套文章里所有具体建议都可能过时——协议在改，库在变，云厂商的默认值每年不同。但四个轴不会过时，因为它们描述的是密码学材料和使用场景的关系，而不是某个产品的特性。

如果哪天你遇到一个全新的认证方案，别去查它的名字。拿那张判定卡过一遍，你会比它的官网更快搞清楚它是什么。
