# 直接出示：密码、cookie、token、API key

这是三条出示路线里最古老、最简单、也是你现在用得最多的一条。它的定义一句话就说完了：**网络上跑的就是凭据本身。**

麻烦全部来自这一句话的推论。这篇按"麻烦怎么被逐个打补丁"的顺序讲，因为这些东西的名字之所以这么多，就是补丁打多了留下的疤。

## 起点：密码

最初的方案是把密码存在数据库里比对。它坏了两次：数据库泄露时密码全裸；用户在所有网站复用同一个密码。

第一个补丁是**哈希**，而且必须是慢哈希（bcrypt、scrypt、argon2），不是 SHA-256。区别在于：SHA-256 一秒能算十亿次，bcrypt 一秒只能算几千次。对一个被拖库的攻击者，前者是"全部密码瞬间还原"，后者是"每猜一个都要花时间"。

第二个补丁是**加盐**，让两个用同样密码的用户产生不同的哈希，顺便废掉预计算表。

这两个补丁之后，服务端不再持有你的密码原文，只持有一个不可逆的验证材料。**但注意：这一步改变的是存储，不是出示方式。** 你每次登录还在发原文，所以传输链路仍然是那个薄弱点——这也是为什么必须 HTTPS。

## 补丁一：别每次都输密码（会话）

每次请求都带密码有两个问题：密码在网络上反复出现，暴露面大；用户体验差。

于是登录成功后服务端发一个随机的 **session ID**，放进 cookie。之后所有请求带这个 ID，服务端查内存或 Redis 找对应的会话记录。

会话机制的关键性质在服务端：**它是有状态的**。会话记录在服务端的表里，删掉就立刻失效。这让撤销第一次变得干净——"退出所有设备"能真的做到。

代价是水平扩展：多台服务器要共享会话存储。这就是为什么早期 web 应用都得配一个 Redis。

顺带说清一个常被问的问题：cookie 里的 session ID 是对称凭据吗？是的，纯随机串，服务端有一份映射。所以**偷到 cookie 就等于登入你的账号**，这也是 XSS 如此危险的原因（`HttpOnly` 和 `SameSite` 就是在防这个）。

## 补丁二：别把服务端搞成有状态（JWT）

无状态派的想法是：把"你是谁、有哪些权限、什么时候过期"直接写进一个令牌里，签名后发给客户端。服务端每次只验签，不查库。这就是 JWT（RFC 7519）。

好处很实在：任何一台服务器拿公钥就能验，不需要共享会话存储，跨服务很方便。

代价同样实在：**JWT 签出去之后，在过期前无法撤销。** 服务端的表里没有它，删不掉。所有"吊销清单"（revocation list）方案都在把状态又加回来，只是加在了别处。所以实践中 JWT 的有效期通常只有几分钟到几小时，用短期换掉不可撤销这个缺陷。

JWT 最容易出错的地方是它有三个部分（header、payload、signature），只有 signature 受保护。payload 只是 base64，**任何人能读**。别往里放不该公开的东西。

还有一个常见误解：JWT 不等于"安全"。一个 `alg: none` 的 JWT 在实现有漏洞的库里能通过验证；把公钥当 HMAC 密钥的算法混淆攻击也真实发生过。JWT 的安全性完全取决于实现是否严格。

## 补丁三：给程序用的凭据（API key、PAT）

人能用密码，脚本不能。于是有了 API key：一对长随机串，长期有效，直接放在请求头里。

**PAT 就是 API key 的一种**，只是它绑定在某个用户账号上、可以按需缩小权限范围（scope）。GitHub 的 `ghp_xxx` 是典型形态。

它们共享同一个结构性缺陷：**长期有效 + 可被复制 + 常常被塞进配置文件或环境变量**。安全事故里相当大的一部分就是这么来的——token 被提交进公开仓库、被打进 Docker 镜像、被打印在 CI 日志里。

行业现在的方向不是"把 PAT 管得更好"，而是**让它在多数场景下不再必要**：CI 里用 OIDC 换临时凭据（第 10 篇），云上用角色假定，git 用 SSH key 或短期 token。凡是能换成短期签发的地方，都应该换。

## 补丁四：别让第三方拿你的密码（OAuth）

"用 Google 登录"的动机很直接：不要让每个小网站都存一份你的密码。

OAuth 2.0（RFC 6749）的做法是引入三方：你、你信任的授权服务器（Google）、你要用的应用。授权服务器发一个 access token 给应用，应用拿它去访问资源。**你的密码从来没有离开过 Google。**

这里有一个必须说清的区分，因为它是整个领域最常见的错误：

- **OAuth 是授权（authorization）协议，不是认证（authentication）协议。** 它回答"这个应用能做什么"，不回答"你是谁"。
- 想说"你是谁"，要在 OAuth 上加一层 **OIDC**（OpenID Connect），它额外发一个 ID token，里面的 `sub` 字段才是身份。

历史上大量"用 Facebook 登录"漏洞就来自这个混淆：应用把"这个 token 有效"错误地当成了"这是本人"。OIDC 就是为了堵这个口子而存在的。

## 补丁五：token 太好偷了（DPoP、绑定）

一个 access token 本质上是 bearer token——谁拿到谁能用。攻击者不需要破解任何密码学，转发一下就行。

解法是让 token **绑定到某个只有合法持有者才有的东西**上。RFC 9449 的 DPoP 就是这么做的：客户端生成一对密钥，token 里记录公钥指纹，每次请求用私钥签一个 HTTP 头。偷到 token 的人没有私钥，签不出来。

这里出现了一个有意思的现象：**为了解决对称凭据的问题，引入了一个非对称密钥对。** 这几乎是整个领域的缩影——当"可被复制"成为不可接受的缺陷时，方案总是往密钥对那边走。

## 这一类东西的共同骨架

把所有变体放在一起，看它们真正共享的结构：

| 变体 | 时效 | 撤销粒度 | 服务端状态 | 主要风险 |
|---|---|---|---|---|
| 密码 | 长期 | 整体重置 | 哈希 | 复用、钓鱼、拖库 |
| Session ID | 短到中 | 单个会话 | 有状态 | XSS、CSRF |
| JWT | 数分钟 | 基本没有 | 无状态 | 泄露后无法撤销 |
| PAT / API key | 长期 | 单个凭据 | 有状态（查库） | 误提交、日志泄露 |
| OAuth access token | 短 | 单个 token | 看实现 | 中间人、scope 过大 |
| refresh token | 长 | 单个 | 有状态 | 泄露后长期有效 |
| magic link | 一次性 | — | 有状态 | 邮箱被接管、链接转发 |
| 恢复码 | 一次性 | 单条 | 有状态 | 明文存放 |

这张表可以读出三条规律：

1. **时效越短，可以越不依赖服务端状态。** 这是在不增加复杂度的情况下换取安全的唯一通用手段。
2. **撤销粒度取决于服务端是否记录。** 想撤销干净，就一定得有状态，跑不掉。
3. **这类凭据的安全上限由"谁能读到它"决定。** 所以存放层（第 8 篇）不是配角，它决定了实际强度。

## 什么时候该用这一类的哪一个

- **人每天登录网页**：session cookie。配合短过期 + 滑动续期。
- **跨服务、跨域、需要携带声明**：JWT，但只用于短时效 access token，别当会话用。
- **脚本调 API、无法交互**：尽量换成临时签发的凭据。非要用长期 key，就一份 key 一个用途，能限 IP 就限。
- **第三方应用要访问你的数据**：OAuth + OIDC。永远不要给第三方你的密码。
- **需要一次性、可转发的访问**：magic link 或预签名 URL，并设很短的有效期。

## 一句话收尾

这一类的东西名字最多，因为它们承载了全部"不完美妥协"：能被人记住（密码）、能被脚本用（API key）、能被任意客户端转发（bearer）。它们的共同弱点都可以用同一句话概括：**持有即身份，而持有是很难验证的。**

这也是为什么下一条路——证明而不暴露——虽然麻烦，却在往高价值场景迁移。
