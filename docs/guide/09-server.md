# 服务端那一侧

前面八篇基本是从"使用者"或"攻击者"的视角看。这一篇换成实现者视角，因为服务端的错误模式和用户侧完全不同：用户侧的错误会立刻痛，服务端的错误可以潜伏好几年。

这一篇不讲怎么选方案，讲**如果选定了，哪些地方最容易做错**。

## 口令存储：三个必须同时满足的条件

这是最基础的一条，但每年仍有大型泄露做到三缺一。

1. **用慢哈希。** bcrypt、scrypt、argon2id。不是 SHA-256，不是 MD5，不是"自己写的加盐 SHA256 迭代一万次"。
2. **每个用户独立盐。** 通常由库自动处理，但自己实现时容易漏。
3. **参数随时间提高。** 今天算 100ms 的代价，五年后算 2ms。要有升级机制。

argon2id 目前是首选（有内存硬度，抗 GPU / ASIC）。bcrypt 仍然可接受，注意它的 72 字节输入上限（超过部分被截断，这是一个真实的坑）。

一个容易被忽略的点：**限速和哈希参数是两件事，都要做。** 哈希保护"数据库被拖走之后"，限速保护"数据库还在的时候被在线爆破"。

## 会话设计

有状态 session 和 JWT 的取舍在第 2 篇讲过。这里说的是不管选哪种都要面对的细节：

**会话固定（session fixation）**：登录成功后必须换一个新的 session ID。否则攻击者预先植入的 ID 在登录后变成有效凭据。这个漏洞很老，但仍在出现。

**Cookie 标志**：`HttpOnly`（JS 读不到）、`Secure`（只走 HTTPS）、`SameSite=Lax`（防 CSRF 的默认防线）。三个都设上是基线，不是加分项。

**滑动过期**：用户活跃就续期，不活跃就过期。但要设一个绝对上限，否则一个长期活跃的会话永远不过期。

**并发会话**：能看见"当前登录的设备"并且能踢掉某一台。这不只是功能，它是**用户能自救的唯一手段**。没有这个功能，账号被入侵后用户无从下手。

## 撤销：整个领域最难的工程问题

认证的"验证"很容易，"撤销"极难。原因是撤销需要知道"现在有哪些有效的凭据"——这要求状态。

三种凭据的撤销难度差别巨大：

| 凭据类型 | 撤销方式 | 难度 |
|---|---|---|
| 有状态 session | 删记录 | 简单 |
| 长期 token（PAT） | 标记失效 + 查库 | 简单但需要每次查 |
| JWT | **基本不能** | 极难 |
| 非对称密钥 | 删公钥 | 简单 |
| 同步 passkey | 删公钥 | 简单，但要考虑该平台还同步到哪 |

JWT 的问题是它的好处和坏处是同一个性质：无状态。要在 JWT 上做撤销，你只能：

- 缩短有效期（几分钟）；
- 维护一个黑名单（等于又引入状态）；
- 用版本号（用户表里一个 `token_version`，改密码就加一，但每次还是要查库）。

这三条都在把"无状态"的好处还回去。所以务实的结论是：**JWT 用短有效期，接受"最长几分钟内无法撤销"这个事实，别试图做一个完美的即时撤销。** 真正需要即时撤销的凭据，用有状态的。

## 账户恢复：最常被忽略的入口

这是全篇最重要的一节。

几乎所有安全团队的精力都花在登录路径上，而攻击者去打恢复路径。原因很简单：登录路径被加固了，恢复路径没有。

常见的恢复方式，按强度排序：

```
恢复码（离线保存）> 已登录设备的 passkey > 备用邮箱 > 短信 > 安全问题 > 客服人工
```

**安全问题是最弱的**，因为答案往往能从社交媒体查到。**客服人工**也弱，因为可以被社工。

设计恢复流程的原则：

1. **恢复路径不能比主路径弱太多。** 如果主路径是 passkey，恢复方式是"回答你的生日"，那你实际的安全等级就是生日。
2. **恢复后必须通知所有其他渠道。** 邮件、短信、已登录设备都要提示"你的账号刚刚被恢复"。
3. **恢复后强制重新认证**，并把旧会话全部失效。
4. **加延迟。** 高价值账户的恢复应该等待 24-72 小时，并留出撤销窗口。这比任何技术手段都有效。

## 多租户与枚举

两个常被忽略的细节：

**用户枚举**：登录和"忘记密码"的响应时间/文案不应该泄露"这个邮箱注册过没有"。统一成"如果这个邮箱存在，我们会发一封邮件"。

**时序攻击**：如果用户存在时比对密码要花 100ms，不存在时立刻返回，那么响应时间就泄露了信息。做法是不存在时也算一次假哈希。

这两条属于细节，但它们是自动化攻击侦察的第一步。

## 日志：别把凭据记进去

真实事故里非常高比例的一条：token / 密码被写进日志。

要防的地方比想象的多：请求日志（URL 里的 token）、错误堆栈（把 Authorization 头打出来）、APM 追踪（请求体全量记录）、CI 输出（`set -x` 打印环境变量）、崩溃报告。

一个可操作的做法：在日志层做**脱敏规则**，对已知的敏感 header 和参数名统一替换。不要指望每个开发者记得。

同时要给**安全事件**单独建日志：登录成功/失败、MFA 变更、恢复流程触发、权限提升、token 创建。这些是检测入侵的唯一依据。

## 一次登录该记录什么

一个设计良好的认证事件，至少有：

```
时间、用户 id、结果、认证方式、IP、user agent、
设备标识、地理位置（粗粒度）、是否为首次见到这组合
```

最后一项"是否为首次"是异常检测的核心。它支撑了那些"我们检测到从新设备登录"的提醒——这类提醒的实际防护价值被低估了，因为它是唯一能在**攻击成功后**发现问题的机制。

## 常见的实现错误清单

按出现频率排：

1. **恢复流程比登录弱。**（最高频）
2. **登录成功后没换 session ID。**
3. **JWT 里放敏感数据**（payload 是明文 base64）。
4. **不校验 JWT 的 `aud` 和 `iss`。**
5. **接受 `alg: none`** 或者算法混淆。
6. **token 打进日志。**
7. **没有限速**，六位码可以被在线爆破。
8. **"记住这台设备"永不过期**，把 MFA 降级成单因素。
9. **密码重置链接可复用 / 不过期 / 不绑定用户。**
10. **CORS 配置成 `*` 加 credentials**，等于把 cookie 送出去。

第 8 条值得再提一次，因为它是"看起来是功能、实际是安全降级"的典型。用户勾了"记住我"，之后的 30 天里只有一个设备 cookie——一个可以被复制的对称凭据。

## 一个检验清单

如果你要上线一个登录系统，先用这几个问题自查：

- 数据库泄露了，密码还能被还原吗？（哈希算法 + 参数）
- 一个 token 泄露了，多久能失效？（撤销路径）
- 账号被接管了，用户能自己救回来吗？（活跃会话管理）
- 攻击者不看登录页，会去打哪个入口？（恢复流程）
- 三个月前的异常登录，现在能查出来吗？（日志）

五个问题里有任何一个答不上来，那一处就是真实的弱点。

## 承上启下

这一篇默认的主体是"人"。但现代系统里，请求数量的大头来自**没有人在场的进程**——CI 任务、微服务、定时脚本。它们的认证约束完全不同：不能弹窗、不能按指纹、不能被人工审批。这就是下一篇的主题，也是 PAT 为什么会消失的原因。
