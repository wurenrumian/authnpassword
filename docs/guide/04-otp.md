# 一次性派生：TOTP、HOTP 与第二因素

这条路的形状很特别：**双方共享一个种子，每次出示的都是种子加另一个变量的结果。**

它不是最安全的机制，但它是过去十五年里部署最广的第二因素，所以你几乎一定会遇到它。理解它为什么能被钓鱼，是理解 passkey 的必经一步。

## 从 HOTP 说起

RFC 4226 定义了 HOTP：`HOTP(K, C) = Truncate(HMAC-SHA1(K, C))`，K 是共享密钥，C 是计数器。双方各记一个计数器，每用一次加一，各自算出同一个六位数。

问题是计数器会失步。你的手机和应用各自维护计数，走丢了就全废了。

## TOTP 用时间替代计数器

RFC 6238 把计数器换成时间：`C = floor((现在时间 - T0) / 30)`。每 30 秒换一个值，因为双方都有时钟，不需要通信就能保持同步。

实现上有一个必要的宽容：服务端通常接受前后各一个时间窗（也就是 ±30 秒），因为手机时钟可能慢一点，或者用户输得慢一点。这个"宽限窗口"让暴力破解的成本降低了约三倍——本来只有十分钟一亿分之一的概率，现在变成三个。

标准做法是配合限速和锁定。一个 6 位码的熵只有约 20 比特，也就是一百万分之一，**单靠它自己撑不住在线暴力破解**。这一点很关键：TOTP 的安全性严重依赖服务端的速率限制，不是算法本身。

## 注册时到底发生了什么

扫码的那一刻，服务器把种子发给了你的手机。二维码里是一个 URL：

```
otpauth://totp/Example:alice@example.com?secret=JBSWY3DPEHPK3PXP&issuer=Example
```

`secret` 字段就是种子，base32 编码。**服务器同时也存了一份。**

这一步确立了整个机制的性质：**TOTP 是一个共享秘密。** 你在第 1 篇学到的判据在这里给出否定答案——服务器有你的秘密副本。

所以 TOTP 的安全性不是来自"秘密不出门"，而是来自：

- 每次出示的值不同，用过就过期。
- 截获一个值，只能在极短的窗口内有用。
- 不依赖你能记住什么，手机能算就行。

## 为什么它能被钓鱼

这是全篇最重要的一段。

假设你被引导到 `https://examp1e-bank.com`（注意那个数字 1）。你输入密码，攻击者的假站把它转发给真站，真站要 TOTP 验证码，假站问你要，你输入，假站立刻转发给真站，真站验证通过。整个过程在 30 秒内完成，攻击者拿到了一个真实的会话。

**TOTP 值里不包含任何关于"它是为哪个网站算的"的信息。** 它只是一个基于种子和时间的数，谁拿着这个数去真站都能用。

这就是为什么 FIDO/WebAuthn 的设计者要做一件不同的事：让签名绑定域名。你在第 5 篇会看到，passkey 的签名里包含了 origin，浏览器会拒绝在任何其他域名上使用同一个凭据。

换句话说：**passkey 抗钓鱼不是因为它"更安全"，而是因为它把"给谁用"编码进了签名本身。** TOTP 在架构上就没有这个位置可放。

## HOTP 还在用的地方

HOTP 没有死，它在两个场景里还常见：

- **硬件令牌**：那些按键出六位数的钥匙扣（RSA SecurID 一类）。每次按一下计数器加一，屏幕上没有时钟。
- **恢复码**：一串一次性密码，本质就是 HOTP——用一个少一个。构造上简单得多：服务端生成一堆随机串，存哈希，用掉就划掉一个。

恢复码这件事值得单独说：**它是整个 MFA 体系里最常被忽略的弱点。** 你精心保护了第二因素，但恢复码通常是一张躺在邮件里、或者打印在纸上的明文列表。攻击者不需要攻破 TOTP，只需要找到恢复码。

## 第二因素的位置

TOTP 的典型用法是"密码 + TOTP"。这里有两个因素，因为它们是**两种不同类型的东西**：

- 你知道的东西：密码。
- 你持有的东西：装着种子的手机。

"两类"这个要求很重要，因为"两个密码"不算多因素——它们都是"你知道的"，一个被钓走另一个也可能被钓走。第 7 篇会把这件事算清楚。

## 推送确认：不是密码学

和 TOTP 并列出现在认证器 app 里的另一种方式是推送确认：登录时手机弹一个"是你吗？"，你点“是”。

这背后**没有密码学**。它是应用和服务端之间的一条已认证长连接，服务端把登录请求作为消息推给这个连接，应用回一个答复。

它的安全性完全依赖：

- 那条长连接本身没被接管（通常靠设备上的长期对称密钥）。
- 你真的看清了你在确认什么。

早期版本只问“批准吗”，这导致了大量"疲劳攻击"：攻击者不停推送，用户烦了就点了同意。现在的标准做法是**数字匹配**——屏幕上显示 42，你必须在手机上选 42。这把"确认"变成了一次真正需要人注意的交互。

这是一个人机交互安全（usable security）的典型案例：机制设计得再好，如果人的默认反应是"点同意"，它就不成立。

## 邮件和短信验证码

技术上和 OTP 同类，但信道弱得多：

- 短信可被 SIM 交换攻击（攻击者补办你的号码），或者被 SS7 拦截。
- 邮件取决于邮箱本身的安全性——而邮箱往往就是密码重置的入口，形成循环依赖。

NIST SP 800-63B 已经把 SMS 列为"受限"（restricted）而非禁止。意思是：能用，但不该是唯一手段，尤其是高价值账户。它的价值在于覆盖面（人人有手机号）和防自动化（提高批量攻击成本），不在于强度。

## 什么时候该选它

TOTP 在今天的正确定位是：**一个普遍可用、成本极低的第二因素，比没有强得多，但不该被当成终点。**

- 对普通用户产品：提供 TOTP，比只发短信好，比只发邮件好得多。
- 对高价值账户（邮箱、代码仓库、云控制台、财务）：应该上 passkey 或硬件密钥，TOTP 留作备用。
- 对内部系统：如果全员有手机，TOTP 部署成本最低，可以接受。

有一个务实的排序，从弱到强：

```
无 MFA < 邮件码 < 短信码 < TOTP < 推送数字匹配 < passkey（同步）< 硬件密钥（不可导出）
```

注意"同步 passkey"和"硬件密钥"的区别在后面几篇会讲清楚：同步 passkey 存在云端，可以在新设备上恢复；硬件密钥里的私钥永远出不来。前者方便得多，后者更强。两者都抗钓鱼。

## 这一类的骨架

| 名字 | 共享什么 | 变化源 | 单次有效 | 抗钓鱼 |
|---|---|---|---|---|
| HOTP | 种子 | 计数器 | 是 | 否 |
| TOTP | 种子 | 时间 | 是 | 否 |
| 恢复码 | 随机串 | 用过作废 | 是 | 不适用 |
| 推送确认 | 设备长连接 | 会话 | 是 | 弱（看是否数字匹配） |
| 邮件 / 短信码 | 服务端生成 | 会话 | 是 | 否 |

三条规律：

1. **它们全部是对称的。** 没有一个能避免"服务端也有一份"这个事实。
2. **一次性只降低窗口，不改变信任结构。** 被钓鱼时窗口足够短反而更糟——你发现不了。
3. **抗钓鱼需要一个能判断"给谁"的位置。** 这条路上所有方案都缺这个位置。这正是 passkey 存在的理由。
