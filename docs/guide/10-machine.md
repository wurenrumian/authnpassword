# 机器身份

前面九篇默认的主体是"人"。但真实系统里，请求量的大头来自**没有人在场的进程**：CI 任务、微服务、定时脚本、批处理。

这一类没有第 7 篇的那套工具可用——不能弹窗、不能按指纹、不能被人工审批、不能"记住这台设备"。所以它的加固手段只剩两条：**短寿命**和**绑定具体目标**。

这一篇讲这两条怎么落地，以及为什么 PAT 正在被淘汰。

## 机器凭据的特殊约束

| 约束 | 后果 |
|---|---|
| 无人交互 | 不能做 MFA、不能确认推送 |
| 要能自动运行 | 凭据必须能被程序读到 |
| 常常跑在共享环境 | 环境变量、临时文件可能被同主机其他进程读到 |
| 生命周期长（服务一跑几年） | 凭据容易变成"永不过期" |
| 数量多 | 一个中型公司可能有上万份凭据 |

关键词是**"能被程序读到"**。这意味着凭据必然以某种形式出现在进程可访问的内存或文件里，于是"不可复制"这个性质在机器世界里很难保住。

## 问题：长期静态凭据

传统做法是发一个 API key，写进配置或环境变量，一直用。

这个模式的所有问题都能追溯到一点：**它同时是长期的、可复制的、静态的。**

- 一旦泄露，有效期是"直到有人发现"。
- 它躺在某个配置文件里，会被备份、被打包、被复制到测试环境。
- 轮换需要协调所有使用方，所以没人做。

第 8 篇讲的"秘密清单"问题在这里最严重：你很难知道一个用了三年的 key 到底被哪些东西引用着。

## 解法一：让平台替你签发短期凭据

核心思路是**消除静态凭据**。程序不再持有一个长期秘密，而是在启动时用"我是谁"这个事实去换一个短期凭据。

三个具体机制：

**云上的实例身份。** EC2 实例元数据服务、GCP 的 metadata server、Azure 的 managed identity。运行在机器上的进程请求 `http://169.254.169.254/...`，平台验证"这个请求确实来自这台实例"，然后返回一个短期凭据。**没有任何密钥需要配置。**

**Kubernetes 的服务账号令牌。** 现代做法是 projected token：kubelet 把一个有时效的 JWT 挂进容器，里面有这个 Pod 的身份。它自动轮换，不需要你管理。

**CI 的 OIDC。** GitHub Actions、GitLab CI 都能给你的流水线签发一个 OIDC token，里面有仓库、分支、工作流的信息。云平台（AWS、GCP、Azure）可以配置成"信任这个 issuer，并且只接受来自 `repo:org/app:ref:refs/heads/main` 的 token"，然后换成短期云凭据。

这第三种是你个人最容易用上的：**它把 PAT 直接消掉了。** 以前 CI 里放一个长期 AWS key，现在是流水线自己去换，有效期一小时，而且只在 main 分支上能换到。

## 解法二：工作负载身份

在服务网格和零信任架构里，每个工作负载有自己的身份，用 mTLS 证书表达。

**SPIFFE** 是这个方向的标准化：一个工作负载的身份是一个 URI，比如：

```
spiffe://cluster.local/ns/prod/sa/payments
```

含义是"prod 命名空间下、payments 服务账号的工作负载"。这个身份由集群的控制面签发成短期证书（通常几小时），自动轮换。服务之间互相验证证书，不需要任何共享密钥。

关键性质：**身份由平台分配，不靠配置。** 你不能"抄一份身份到别处"，因为证书绑定的是运行时的证明（在 k8s 里是 service account token，在 VM 上是实例证明）。

## 解法三：把长期凭据换成可交换的

有些场景确实需要一个长期的东西，比如跨云、或者对方的系统不支持 OIDC。这时可以做**凭据交换**：

- 用一个 OIDC token 换一个目标系统的 token（RFC 8693 token exchange）。
- 用云 A 的身份换云 B 的凭据（工作负载身份联邦，比如 AWS 的 IAM Roles Anywhere、GCP 的 Workload Identity Federation）。

方向是一致的：**长期的东西越来越少，每次访问都现场换一次。**

## 三种主体，三种加固

把前面几篇的结论并排看，差别就很清楚了：

| | 人 | 设备 | 进程 |
|---|---|---|---|
| 加固手段 | 多因素 | 硬件绑定、设备证明 | 短寿命、绑定目标 |
| 不能做什么 | 记不住长密钥 | 不能生物识别 | 不能交互 |
| 最佳凭据 | passkey | TPM 中的密钥 | 短期 SVID / OIDC token |
| 主要威胁 | 钓鱼、复用 | 被盗、被克隆 | 配置泄露、日志泄露 |
| 撤销粒度 | 单设备 | 单设备 | 单工作负载 |

这三列不是同一件事的三个版本，是**三种不同的安全模型**。把它们混在一起谈，是很多架构讨论跑偏的原因。比如"为什么服务间不能用 passkey"——因为 passkey 需要一个能判断域名、能弹窗的浏览器，服务没有这些。

## 设备身份：中间的第三种

设备身份常被忽略，但它有自己的位置：

- **设备证书**：企业环境里给每台笔记本发一份证书，用来连 VPN、连 Wi-Fi。私钥在 TPM 里。
- **设备证明**（attestation）：设备用 TPM 证明"我运行的是未被篡改的固件"。这是零信任里的设备健康检查。
- **设备绑定**：把用户的凭据绑定到具体设备，换设备就要重新认证。这是"记住这台设备"的正经版本。

设备身份回答的是"这台机器可信吗"，和"这个人是谁"、"这个进程是谁"是三个独立的问题。在零信任架构里，三者都要，而且是分开验证的。

## 为什么 PAT 会消失

回到你的列表里的那一项。

PAT 之所以存在，是因为它解决了一个真实问题：**脚本需要一个能长期使用的凭据**。它的替代品在很长时间里不存在，或者太重（自建 OIDC、搭一套 SPIFFE 控制面）。

现在替代品成熟了，而且是零成本的（GitHub Actions 里换 OIDC 只要改几行 YAML）。于是 PAT 的唯一优势只剩"简单"。

这解释了一个趋势：**PAT 正在从"默认做法"退化成"最后手段"。** GitHub、GitLab、云厂商都在推 OIDC，同时给 PAT 加越来越多的限制（强制过期、强制 scope、审计）。

不是 PAT 变差了，是它的问题终于有了便宜的解法。

## 一个可执行的迁移路径

如果你现在有一堆长期凭据，务实的顺序是：

1. **盘点。** 列出所有长期凭据和它们的引用位置。这一步最难，通常能发现一堆没人认领的。
2. **给每一个标注"谁能换掉它"。** 能换 OIDC 的换 OIDC，能换实例角色的换实例角色。
3. **剩下的，强制过期 + 自动轮换。** 用 Vault 或者云厂商的 secret manager 做动态凭据。
4. **加审计。** 记录每次使用，找出"三个月没用过"的，删掉。

第 4 步往往能砍掉一半。**没被使用的凭据是纯风险，零收益。**
