# 授权与委托：OAuth、OIDC、JWT、SAML

前面五篇都在回答"你是谁"（authentication）。从这一篇开始回答"你能干什么"（authorization）。这两个词在中文里都叫"认证/授权"，混用之普遍，已经到了不澄清就没法讨论的程度。

一句话区分：**认证是出示身份证，授权是检查你的票能不能进这个厅。**

## 为什么授权需要单独的协议

单机时代，授权就是数据库里一个 `is_admin` 字段，简单。

一旦有了第三方应用，问题变成："一个第三方应用想访问我在另一个服务上的数据，怎么在不给它我密码的前提下做到？"这就是 OAuth 要解决的问题。

如果不用 OAuth，唯一的办法是把密码交给第三方应用。这带来三个无法解决的问题：

- 应用能看见你的密码，也能看见你的全部数据，无法限制范围。
- 你无法单独撤销某个应用的访问，除非改密码，而那会踢掉所有设备。
- 应用被入侵，你的密码就泄露了。

OAuth 的核心想法是：**引入一个授权服务器作为中间人，由它签发受限、可撤销的凭据。**

## OAuth 2.0 的四个角色

| 角色 | 是什么 | 例子 |
|---|---|---|
| Resource Owner | 有数据的那个人 | 你 |
| Client | 想访问数据的应用 | 某个第三方日历 app |
| Authorization Server | 签发令牌的服务器 | Google 的账号服务 |
| Resource Server | 存数据的服务器 | Google Calendar API |

这四个角色是理解所有 OAuth 讨论的前提。说"token 泄露了"时，先问是哪个角色泄露了——差别很大。

## 授权码流程，一步一步

这是最常用、也最该先理解的流程：

1. 应用把你重定向到授权服务器，带上 `client_id`、`redirect_uri`、`scope`、`state`。
2. 你在授权服务器上登录（这一步是认证，和 OAuth 无关）。
3. 授权服务器问你："这个应用想读你的日历，同意吗？"
4. 同意后，浏览器被重定向回 `redirect_uri`，URL 里带一个 **authorization code**。
5. 应用在**后端**拿这个 code 去换 token（这次是服务器对服务器，带 `client_secret`）。
6. 拿到 access token（短期），可能还有一个 refresh token（长期）。
7. 应用用 access token 访问资源服务器。

第 5 步是设计的关键：**code 经过浏览器，token 不经过浏览器。** 即使 code 被截获，没有 `client_secret` 也换不到 token。

## PKCE：给不能保守秘密的客户端用

手机 app 和单页应用没法安全地存 `client_secret`（app 可以被逆向，JS 源码是公开的）。RFC 7636 的 PKCE 就是为这个场景设计的：

1. 应用生成一个随机串（code_verifier），算它的哈希（code_challenge）。
2. 第一步只发 challenge。
3. 换 token 时发 verifier，服务器验证哈希对得上。

效果：截获 code 的人没有 verifier，换不到 token。这本来是给公共客户端的补丁，现在 OAuth 2.1 草案建议**所有客户端都用**，因为没有理由不用。

## OAuth 不是认证协议

这是整个领域最贵的一个错误。

OAuth 的 access token 回答"这个应用能访问什么"，它**没有规定 token 里必须包含用户身份**。历史上的"用 Google 登录"实现，很多是拿 access token 去调一个用户信息接口，然后信任返回结果。

这个模式有一个致命漏洞：**攻击者可以拿自己账号的 token，配上一个受害者的 app**。因为协议里没有说"这个 token 是发给这个应用的"。攻击者注册一个恶意应用，拿到一个针对自己账号的 token，然后把这个 token 当成"已经通过认证"的凭据交给受害者的应用。如果应用只看"token 有效"，就会被冒充。

OIDC 就是为此而生的。

## OIDC：在 OAuth 上加一层身份

OpenID Connect 做的事很简单：在授权码流程里多要一个 scope（`openid`），授权服务器额外返回一个 **ID token**。

ID token 是一个 JWT，里面有：

| 字段 | 含义 |
|---|---|
| `iss` | 谁签发的 |
| `sub` | 这个用户在你这里的稳定标识 |
| `aud` | 这个 token 是发给哪个 client 的 |
| `exp` / `iat` | 有效期 |
| `nonce` | 防止重放 |

**`aud` 和 `nonce` 就是堵上面那个漏洞的。** 应用必须验证 `aud` 是自己的 `client_id`，否则拒绝。这一条检查如果漏了，OIDC 就退化成有漏洞的 OAuth。

## JWT 在这个体系里的位置

第 2 篇已经讲过 JWT 作为 bearer token 的性质。在授权语境里补三点：

**一、JWT 是一种格式，不是一个协议。** 它可以承载 OIDC 的 ID token，可以是 OAuth 的 access token，也可以是你自己定义的东西。说"我们用 JWT 做认证"没有信息量。

**二、签名验证不等于授权。** 验签只证明"这个 token 是某个签发者发的"，不证明"这个用户有权做这件事"。权限检查是另一层，通常由 scope 或后端查询完成。

**三、`scope` 和 `role` 是两种不同的东西。** scope 描述"这个 token 被授予了什么权限范围"，通常是应用级别的；role 描述"这个用户在系统里的角色"。前者在 token 里，后者常在数据库里。混用会让权限模型变乱。

## SAML 与企业 SSO

SAML 2.0 比 OAuth 老，用 XML，主要在企业内部。它的形状：企业有一个 IdP（身份提供者）；员工访问某个 SaaS 时，被重定向到 IdP，登录后 IdP 返回一个签名断言（assertion），说明"这个人是 alice@corp.com，属于这些组"。

和 OIDC 的对比：

| | SAML | OIDC |
|---|---|---|
| 格式 | XML + 签名 | JWT |
| 年代 | 2005 | 2014 |
| 主要场景 | 企业 SSO | 消费级 + 企业 |
| 实现复杂度 | 高（XML 签名规范化是出名的坑） | 中 |
| 移动端 | 差 | 好 |

两者在能力上重叠很多。新系统一般选 OIDC；但企业客户往往只支持 SAML，所以 SaaS 通常两个都得做。

## 一堆相关的词，各归其位

| 词 | 它解决什么 |
|---|---|
| scope | 请求的权限范围，授权时由用户同意 |
| audience (`aud`) | 这个 token 是给谁的，防止被挪用 |
| DPoP（RFC 9449） | 把 bearer token 绑定到客户端密钥，防转发 |
| token exchange（RFC 8693） | 用一个 token 换另一个，支持链式委托 |
| mTLS 绑定 | 把 token 绑定到客户端证书（比 DPoP 更老的做法） |
| consent screen | 用户同意界面，是授权而非认证的体现 |
| refresh token rotation | 每次刷新发新 refresh token，旧的作废，能发现盗用 |
| back-channel logout | 服务端主动通知登出，解决单点登出的难题 |
| SCIM | 用户/组的自动化同步协议，和认证无关 |
| OAuth 2.1 | 草案，收紧了若干不安全做法（隐式流程、密码模式） |

## 委托的本质

在所有细节之下，OAuth 做的是**委托**：你把自己的一部分权限，临时授予一个第三方，并且可以收回。

委托有三个必须能回答的问题：

1. **范围**：授予了什么？（scope）
2. **对象**：给谁的？（audience / client_id）
3. **期限**：多久失效，怎么撤回？（exp / revocation）

任何 OAuth 实现，只要这三个问题有一个答不清楚，就会出问题。反过来，你看到一个陌生的授权方案，也可以拿这三个问题去检验它。

## 一个反直觉的观察

OAuth 被设计出来是为了**减少**密码的传播。但它引入了新的问题：token 变成了一种新的、可被转发的凭据，而且数量比密码多得多——一个用户可能有一百个 token 挂在不同的应用上。

于是有了一个持续的军备竞赛：bearer 太容易转发 → 引入 DPoP / mTLS 绑定 → 绑定需要客户端密钥 → 客户端密钥需要保管 → 保管又回到老问题（第 8 篇）。

这套文章一直强调的那句话在这里再次成立：**每一层的解决方案都会把问题搬到下一层，而不是消灭它。**

## 承上启下

到这里，机制、授权都讲完了。但还有一个基础问题一直悬着：**"两个因素"到底在数什么？** 为什么"密码 + 密码"不算多因素，"密码 + TOTP"算？这个问题看起来琐碎，实际决定了你怎么设计一个真正成立的 MFA——第 7 篇。
