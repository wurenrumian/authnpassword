# 挑战签名：SSH、GPG、mTLS、Kerberos

上一篇的核心弱点是"网络上传的就是凭据本身"。这一篇走另一条路：**网络上什么都不传，只传一个签名。**

## 一次 SSH 登录的完整过程

不讲原理，先看一次真实连接里发生了什么。运行 `ssh user@host`，按顺序发生这些事：

1. 建立 TCP 连接，协商加密算法，服务端出示主机密钥。你第一次连接时看到的 `The authenticity of host ... can't be established` 就是这一步——它在问"你信任这个主机吗"。这是**服务端证明自己**，不是客户端。
2. 客户端和服务端从协商结果派生出一个共享的会话密钥。之后所有流量（包括后面那段签名）都在这个加密通道里。
3. 客户端告诉服务端："我想用这个公钥登录"，发的是公钥**指纹**。
4. 服务端检查 `authorized_keys` 里有没有这个公钥。没有就直接拒绝，连签名都不用做。
5. 服务端发一段随机挑战（session ID 与一些上下文的哈希）。
6. 客户端用私钥签名，发回签名。
7. 服务端用公钥验签。通过则认证成功。

关键在第 6、7 步：**私钥没有被发送，签名被发送了。** 并且这段签名绑定了这次会话的随机挑战，所以在另一条连接上重放无用。

第 4 步也值得注意：这是 SSH 认证的脏活所在。你的公钥要在每台目标机器的 `authorized_keys` 里各登记一份。机器一多，这个登记工作就爆炸了（第 8 步之后讲的 SSH 证书就是来解决它的）。

## 为什么私钥能安全地躺在磁盘上

大量教学材料会说"私钥必须妥善保管"，听起来像一句空话。它实际的含义是：**攻击者拿到私钥文件就等于拿到你的身份，所以这个文件的保护级别必须和密码一样。**

`~/.ssh/id_ed25519` 默认权限是 `600`，这不是传统讲究。如果它是 `644`，同机器上的其他用户能读走它。ssh 客户端甚至会拒绝使用权限过松的私钥文件。

更常见的做法是给私钥加一个口令（passphrase）。此时磁盘上的文件是加密的，每次使用要解密。但每次都输太烦，于是有了 **ssh-agent**：解锁一次，把私钥加载进内存，之后所有 ssh 调用通过本机 socket 让 agent 代为签名。私钥（解密后的形态）不出 agent 进程。

这就引出了第 8 篇要讲的存放层：**agent 是一个"替你做签名运算"的代理，它本身就成为你需要保护的东西。** 任何能连上那个 socket 的本机进程，都能在你不知情的情况下用它签名。这是 agent forwarding 之所以危险的原因。

## SSH key 和你手里的 GPG key 是什么关系

同一种材料（密钥对），不同的**使用者**和**用途**。SSH 用在连接服务器和 git 传输上；GPG 用在签文件、签 git 提交、加密邮件上。

但这两个世界有两条真实的通道，这就是你感觉它们重叠的来源：

**通道一：GPG 的认证子密钥可以当 SSH key 用。** 一个 GPG 密钥结构里可以有多个子密钥，标注为 `[S]`（签名）、`[E]`（加密）、`[A]`（认证）。`[A]` 那个子密钥在密码学上和 SSH key 没有区别。配置 `gpg-agent` 的 `enable-ssh-support`，SSH 就会转而问 gpg-agent 要签名，于是一把 GPG 密钥可以同时管 git 提交签名和服务器登录。私钥始终在 gpg-agent 里（或者在你插着的智能卡里）。

**通道二：SSH key 可以给 git 提交签名。** Git 2.34 起支持 `gpg.format = ssh`，用 SSH key 签 commit。GitHub 也支持用 SSH key 验证提交签名。

这两条通道是近期才成熟起来的。历史上确实是两套完全分离的工具链，各自有自己的密钥、自己的 agent、自己的格式。如果你读到的教程把两者混为一谈，多半是在讲现在这两条通道，而不是说它们本质相同。

一个实用建议：**安全敏感度高的场景用一把专门的 key，不要一把走天下。** 一把 key 同时用于签名提交、登服务器、加密邮件，出问题时撤销范围会很大。

## mTLS：把客户端证书用在机器之间

TLS 里有一个常被忽略的能力：服务端也可以要求客户端出示证书并验证。这叫做双向 TLS。

在服务网格和零信任架构里，这是服务间认证的标准做法：每个服务有一份证书（通常是短期、自动轮换的），互相验证。Istio、Linkerd 都默认这么干。

它的好处是**不需要应用层写任何认证代码**——认证发生在 TLS 握手阶段。代价是证书管理本身很重，所以实践中一定会有个自动签发和轮换的控制面（SPIFFE 的第 10 篇会讲）。

注意 mTLS 证书和工作负载身份的关系：证书里的主体，通常就是一个工作负载身份（比如 `spiffe://cluster.local/ns/prod/sa/payments`）。它回答"这个进程是谁"，和"这个用户是谁"是两个不同的身份空间。

## Kerberos：这条路里的一个异类

Kerberos 值得单独拿出来，因为它是**用对称密钥实现"证明而不暴露"**的，这和上面所有例子都不同。

它的做法：你第一次登录时，用你的长期密钥（从密码派生）向 KDC（密钥分发中心）证明身份，换来一张 TGT（票据授予票据）。之后要访问某个服务，拿 TGT 去换一张针对该服务的 service ticket。服务端验证这张票——**用自己和服务端之间预先共享的密钥解密**。

你从没把长期密钥发给任何服务，服务端也从不接触它。这确实达到了"不暴露秘密"的效果。但底层材料仍然是对称的，因此它必须依赖一个双方都信任的中心（KDC），并且依赖时钟同步（票据有效期靠时间判断）。

这就是 Windows 域环境里的登录方式。你会听到"域账号""Kerberos 票据""kinit"，都在这套体系里。

它作为对照很有价值，因为它说明：**"不暴露秘密"这个目标可以由两种材料达成，但对称方案必然要引入一个可信中心。** 非对称方案把这个中心省掉了，代价是运算更贵、密钥更长。这是整个领域最根本的一组权衡。

## 签名还能干什么

除了登录，签名这一类还常被用来证明"某段数据是我做的"：

- **git commit 签名**：证明提交者确实是那个身份，而不是把 `user.email` 随便填成别人。GitHub 上那个 "Verified" 徽章就是这个。
- **软件发布签名**：apt、npm、Docker 镜像的签名，让下依赖的人能验证来源。
- **文档 / 邮件签名**：GPG 最原始的用途。
- **固件与启动测量**：UEFI Secure Boot 验证启动链，TPM 记录度量值。这是"设备证明自己"的基础，第 10 篇会碰。

这类签名不涉及"会话"，只是把公钥和一段数据绑在一起。它比登录更简单，也是非对称密码学最早的应用。

## 这一类的共同骨架

| 名字 | 挑战绑定的是什么 | 私钥在哪 | 撤销方式 |
|---|---|---|---|
| SSH key | 会话随机数 | 磁盘 / agent | 从 authorized_keys 删 |
| SSH 证书 | 会话随机数 | 磁盘 / agent | CA 撤销列表 |
| passkey | 域名 + 挑战 | 安全芯片 / 钥匙串 | 服务端删公钥 |
| mTLS | 握手随机数 | 文件 / TPM | 证书吊销 |
| GPG | 待签数据本身 | gpg-agent / 智能卡 | 撤销证书 |
| Kerberos | 票据 + 时间窗口 | KDC（对称） | 票据过期 |

三条规律：

1. **签的东西里必须包含别人无法预测且一次性的内容**，否则可以重放。SSH 用会话随机数，passkey 用挑战加域名，mTLS 用握手随机数。这是这一类能否成立的核心。
2. **私钥的存放位置决定了实际安全等级。** 磁盘上的文件、agent 内存、TPM、YubiKey，是四个完全不同的等级。
3. **撤销普遍比对称方案干净**，因为公钥和私钥是可区分的。你可以只删掉某一台机器的那一份。

## 一个容易忽略的陷阱

签名本身不告诉你"该不该信"。SSH 第一次连接时你看到的指纹，如果不去核对就按了 yes，那次信任是盲目的；之后所有中间人攻击都能通过，因为指纹已经被写进 `known_hosts` 了。

这解释了一类真实的攻击：攻击者在第一次连接时介入，拿到你的密码或让你接受他的主机密钥。防御手段是带外核对指纹，或者用 SSHFP 记录 / 证书体系。

**任何"证明"机制，都有一个"第一次怎么建立信任"的问题绕不过去。** 非对称解决了"传输中不暴露"，但没解决"对方是不是真的"。这个问题在 passkey 那里由浏览器和域名系统分担了一部分（第 5 篇），在证书体系里由 CA 分担。它是一个独立的问题，值得单独记住。

## 承上启下

三条路还差一条：既不是直接把秘密递出去，也不是稳定的密钥对签名，而是每次都现算一个不重复的数。这条路解决的是"我手上只有一个便宜的小设备（手机），但我想让它成为第二道门"——第 4 篇。
