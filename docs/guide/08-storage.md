# 存放与生命周期

这一篇处理你觉得最杂的一块：密码管理器、密钥保管箱、KMS、TPM、Secure Enclave、ssh-agent、硬件密钥、操作系统钥匙串。

它们看起来都在"存东西"，但它们解决的是**四个不同的问题**。分清这四个，这一堆名字就自动归位了。

## 四个不同的问题

| 问题 | 谁来解 |
|---|---|
| 人记不住长秘密，怎么让人能用 | 密码管理器、钥匙串、agent |
| 秘密不该以明文躺在磁盘上 | 加密存储、硬件密钥、TPM |
| 秘密不该被复制出去 | 硬件不可导出（TPM、Secure Enclave、硬件密钥） |
| 服务器端怎么管大量密钥 | KMS、HSM、Vault |

一个工具通常解决其中一个或两个。这就是为什么它们不可互换：YubiKey 解决不了"我要在服务器上签一百万次"，KMS 也解决不了"我手机丢了怎么恢复"。

## 人的一侧：密码管理器

主密码加密整个库，库同步到各处。你只需要记住一个强密码（或者用生物识别解锁）。

它解决的核心问题不是"记住密码"，而是**让每个网站有独立的随机密码变得可行**。人不可能记住四十个不同的强密码，所以如果没有管理器，复用就不可避免。

安全模型是：**所有鸡蛋放在一个篮子里，但篮子锁得很紧。** 这个模型的合理性来自一个事实——现实中的攻击是分散的、机会主义的，不是针对你个人的。集中管理把攻击面从四十个弱口令缩减成一个强口令。

它的弱点也在这里：主密码一旦泄露，全部泄露。所以主密码必须非常强，且绝不在任何其他地方使用。

关于"云同步的密码管理器安不安全"这个常见问题，技术上的答案是：**同步的是密文，服务商理论上解不开**（前提是采用零知识设计，比如 Bitwarden、1Password 的模型）。但你要接受一个前提：恢复流程能做多强，取决于服务商允许你在忘记主密码时怎么恢复。如果允许"用邮箱重置"，那邮箱就成了实际的安全上限。

## Google 密码管理器 / 密钥保管箱

你点名的这个属于同一类，但它有一个额外特征值得单独说：**它同时是 passkey 的同步后端。**

第 5 篇讲过：同步 passkey 的私钥被加密上传到云端，在设备间同步。Google 的那套服务就是这个云端的实现。所以你会在同一个界面里看到：

- 网站的密码（对称秘密）
- passkey（非对称私钥）
- 有时还有 TOTP 种子（对称种子）
- 地址、支付卡等（非认证数据）

这就是为什么你会觉得"这东西和认证是一回事"。它不是。它是一个**容器**，里面装了好几种不同性质的东西。这和 YubiKey 是同一个结构——一根钥匙里装了好几套互不相干的机制。

理解成容器之后，有一件事就清楚了：**容器本身不提供安全性，容器的解锁方式才提供。** 一个密码管理器用主密码解锁，那它的安全等级就等于那个主密码；用设备生物识别解锁，就等于那台设备的安全芯片。

## 操作系统钥匙串

Windows Credential Manager、macOS Keychain、Linux 的 libsecret / gnome-keyring。

它们做的是同一件事：给本机应用提供一个"存密码/密钥"的标准位置，并按用户账户隔离。应用通过 API 存取，用户不需要知道文件在哪。

它们通常是密码管理器的底层。1Password 在 macOS 上可以利用 Secure Enclave 保护它的密钥；浏览器把 cookie 加密密钥存在钥匙串里。

## 开发者的一侧：agent

**ssh-agent** 和 **gpg-agent** 是同一类东西：一个常驻进程，把私钥加载进内存，替你做签名运算。这样你不用每次输口令，私钥也不用反复从磁盘解密。

关键性质：**agent 本身变成了一个需要保护的信任边界。** 任何能连上它 socket 的本机进程，都能让它签名。所以：

- 本机被入侵 = agent 里的所有密钥失守。
- `ssh -A`（agent forwarding）把这个 socket 转发到远端服务器 = 那台服务器上的任何进程都能用你的密钥。这就是为什么安全指南一律反对 agent forwarding，推荐用 ProxyJump 代替。
- agent 有确认机制（`ssh-add -c`，每次使用需要确认），但很少有人开，因为它很烦。

这是"便利与安全权衡"的一个标准案例，而且它的名字很误导——人们以为 agent 是"保管"，实际是"暴露的接口"。

## 硬件：四个不同的东西

这四个经常被一起提，但定位完全不同。

**TPM**：主板上的芯片，绑定这台机器。能做密钥运算、能存少量密钥、能做启动测量。私钥不可导出。典型用途：BitLocker 的全盘加密密钥、Windows Hello 的凭据。

**Secure Enclave / Strongbox**：手机和部分电脑里的独立安全芯片，和主 CPU 隔离。私钥不可导出。典型用途：Face ID / Touch ID 背后的密钥、同步 passkey 的本地部分。

**HSM**：独立的硬件设备，给服务器用。密钥在设备内运算，不出设备。典型用途：CA 的根密钥、支付系统的密钥。贵，需要专门运维。

**硬件密钥（YubiKey 一类）**：插在钥匙串上的小设备。私钥不可导出。典型用途：passkey、SSH key、PIV 智能卡、TOTP 令牌。

它们的共同点只有一个：**私钥在物理上不可导出。** 这让"被复制"这条攻击路径失效。差别在**绑定对象和用途**：TPM 绑机器，Secure Enclave 绑个人设备，HSM 绑机房，硬件密钥绑人。

有一个实用细节：YubiKey 里同时有 FIDO2、PIV、OpenPGP、OATH 四套功能，各自有独立的槽位和 PIN。买一根钥匙不等于"有了 passkey"，你只是获得了一个能装多种机制的容器——和第 5 篇说过的"认证器 app 是容器"完全同构。

## 服务器的一侧：KMS 与 Vault

在服务端，"密钥放在配置文件里"是不能接受的，因为：

- 配置文件会进 git、进镜像、被备份。
- 轮换密钥需要重启服务。
- 无法审计"谁在什么时候用了这个密钥"。

**KMS**（AWS KMS、GCP KMS、Azure Key Vault）提供的模型是：**密钥存在服务里，你调用 API 让它签/解/加密，你永远拿不到密钥本身。** 加上访问策略和审计日志，就得到了可控、可审计、可轮换的密钥使用。

**HSM** 是这个模型的物理版本，用在自己的机房里。

**Vault**（HashiCorp）是另一层：它做秘密的分发和动态生成。典型用法是"应用启动时向 Vault 要一个数据库密码，Vault 现场创建一个只用一小时就过期的账号"。这就是**动态凭据**，比"存一个长期密码"强得多，因为泄露的窗口很短。

**SOPS / sealed-secrets** 是另一类：把秘密加密后和代码一起放在 git 里，解密密钥放在 KMS 里。它解决的是 GitOps 场景的"秘密怎么进仓库"。

## 生命周期：六个阶段

存放只是生命周期里的一个点。完整的循环是：

| 阶段 | 要做的事 | 常见失败 |
|---|---|---|
| 生成 | 用足够的随机源 | 用 `Math.random()`、用可猜的字符串 |
| 分发 | 安全地交到使用方 | 通过 Slack / 邮件 / 工单系统传 |
| 使用 | 最小权限、短时效 | 一份 key 权限过大、永不过期 |
| 轮换 | 定期换新 | 从来不做，因为"怕弄坏" |
| 撤销 | 立即失效 | 没有清单，不知道哪些在用 |
| 销毁 | 从所有副本删除 | 备份里还留着 |

最容易被跳过的是**轮换**和**撤销**，因为这两件事都要求你先知道"这东西在哪儿被用了"。这就是为什么"秘密清单"（secret inventory）比"秘密存储"更难也更重要。

一个诊断问题：**如果这个 token 明天泄露了，你能不能在一小时内把它全部换掉？** 答不出来，说明生命周期管理缺失。

## 一个反直觉的结论

人们常以为存放层是"把东西放好"，所以越集中越安全。实际关系更微妙：

**集中的好处是可管理**（能审计、能轮换、能撤销），**集中的坏处是单点**。所以正确的方向不是"分布存放"或"集中存放"，而是**集中管控 + 分散使用**：

- 密钥存在一个受控的地方（KMS、Vault）。
- 使用方通过短期的、自动获取的凭据来访问。
- 没有任何长期密钥躺在应用的配置文件里。

这就是所谓的"secret zero"问题——你总得有一个初始秘密来获取其他秘密。现代的做法是把这个初始秘密也去掉，让工作负载直接用自己的身份去换（第 10 篇）。

到现在为止，我们大部分时间站在攻击者或用户的视角看。下一篇换位置：**如果你是写这个登录系统的人，要注意什么。** 那一侧的错误模式和用户侧完全不同，而且更容易被忽略——因为用户侧的错误会立刻痛，服务端的错误可以潜伏几年。
