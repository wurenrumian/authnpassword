# passkey 与 WebAuthn

这一篇是这套文章里技术密度最高的一篇，因为它要同时回答四个常见问题：passkey 到底是什么？为什么它抗钓鱼而别的都不行？它存在哪儿？为什么"同步"和"硬件"是两种安全等级？

先说清一件事：**passkey 是 WebAuthn 的一个用法，"密钥对 + 挑战签名 + 域名绑定"是它的全部机制。** 你不需要记住一堆 API 名称，只需要理解那三个性质如何组合。

## 术语先对齐

四个词经常被混用，关系是嵌套的：

| 词 | 是什么 |
|---|---|
| **FIDO2** | 一整套规范的商业名称，包含 WebAuthn 和 CTAP2 |
| **WebAuthn** | 浏览器 API 规范（W3C）。页面通过它请求一次凭证操作 |
| **CTAP2** | 认证器与客户端之间的协议（FIDO 联盟）。规定了硬件密钥怎么和电脑说话 |
| **passkey** | 一个 WebAuthn 可发现凭据（discoverable credential）的商业叫法 |

所以：passkey ⊂ WebAuthn ⊂ FIDO2。说"passkey 是一个 WebAuthn 凭据"是准确的；说"passkey 是一个 API"就错位了。

## 注册时发生了什么

用户在页面上点"创建 passkey"，实际流程：

1. 页面调用 `navigator.credentials.create()`，传入 `rp.id`（你的域名，比如 `example.com`）、一个随机 `challenge`、用户信息。
2. 浏览器把这个请求交给认证器（平台认证器——手机/电脑的芯片，或漫游认证器——一根 USB 钥匙）。
3. **认证器自己生成一对新密钥。** 私钥留在认证器里，不可导出。
4. 认证器把 `credential ID`（这个凭据的随机标识）、公钥、以及**用私钥签名的 attestation** 返回给浏览器。
5. 浏览器把 `origin`、`rp.id`、`challenge`、`clientDataJSON` 的哈希一起纳入被签名的数据。
6. 服务端验证签名、验证 origin 和 rp.id 匹配、存下 `credential ID` 和公钥。

**第 5 步是全部安全性的来源。** 被签名的内容里包含了"这是给 `example.com` 的一次操作，challenge 是这一串"。任何第三方都无法在别的域名上复用这次签名。

## 登录时发生了什么

1. 页面调用 `navigator.credentials.get()`，带上 challenge 和 `rp.id`。
2. 浏览器根据 `rp.id` 找出对应的凭据，让用户选（或触发一个确认）。
3. 认证器用私钥签名，签名内容包含 `authenticatorData`（里含 rp.id 的哈希）、`clientDataJSON`（里含 origin 和 challenge）。
4. 服务端用存下的公钥验签，检查 rp.id 对得上、challenge 是本次发出的、计数器（如果启用了）没有倒退。

用户侧的操作可能是指纹、人脸、PIN，或者只是插上钥匙按一下。**这些是本地解锁手段，不是网络传输的凭据。** 这是 passkey 和"密码 + TOTP"最本质的区别：生物特征从不离开设备，也从不发给服务器。

## 抗钓鱼是怎么实现的

这是全篇的核心，值得慢一点。

钓鱼攻击的本质是让你在一个**假域名**上完成一次真实的认证动作，然后攻击者把你的响应转发给真站。TOTP 挡不住，因为 TOTP 值不携带域名的任何信息。

WebAuthn 的防线有三层，缺一不可：

**第一层：浏览器读取真实 origin。** 页面 JavaScript 不能伪造 origin——它由浏览器在进程外填充进 `clientDataJSON`。攻击者即使完全控制了页面脚本，也改不了这个字段。

**第二层：认证器强制 rp.id 匹配。** 浏览器只在凭据的 rp.id 与当前页面 origin 匹配（同域或子域）时才会把该凭据提供给页面。在 `examp1e-bank.com` 上，`example.com` 的凭据根本不可见。

**第三层：私钥从不离开认证器。** 即使攻击者让用户在他的假站上完成了签名，签名里绑定的是 `examp1e-bank.com`，转发给真站验证必然失败。

所以抗钓鱼不是"更严格的检查"，而是**在密码学材料里放了一个无法篡改的域名标签**。TOTP 架构上没有这个位置。

## passkey 存在哪里

这个问题决定实际安全等级，也是行业里争论最多的一点。

**平台认证器（platform authenticator）**：手机或电脑里的安全芯片。私钥在 TPM / Secure Enclave / Strongbox 里，物理上不可导出。可以用生物识别解锁。

**漫游认证器（roaming authenticator）**：一根 USB / NFC 硬件密钥。私钥在钥匙里，同样不可导出。

**同步 passkey（synced passkey）**：这是 passkey 相对传统 FIDO 的**新增部分**。凭据可以被加密后上传到云（iCloud 钥匙串、Google 密码管理器），再同步到你的其他设备。

同步用的是**端到端加密**：上传的是密文，平台也解不开，解密密钥通过设备间的安全通道传递。听起来不错，但有一个结构性事实需要承认：**同步意味着私钥不止一份，而且恢复流程的强度变成了整个体系的上限。**

具体后果：

- 你的 Apple ID / Google 账号被接管，攻击者可能通过账号恢复流程拿到你的 passkey。**passkey 的安全上限，等于你云账号的安全上限。**
- 这个云账号本身通常也用 passkey 保护（厂商会这么推），但恢复路径往往还是手机验证码或旧密码。
- 从"不可导出的私钥"变成了"可以在多个设备上出现的私钥"，只是导出路径被控制得很好。

**不可同步的硬件密钥仍然是更强的形态**：私钥只在那根东西里，丢了就没了（所以必须买两根，一根备用）。代价是便利性明显更差。

所以正确的说法不是"passkey 比 TOTP 安全"，而是：

```
TOTP < 同步 passkey ≤ 硬件密钥
```

同步 passkey 和硬件密钥都抗钓鱼，这是它们共同的、也是最重要的优势。它们之间差的不是抗钓鱼能力，而是**私钥是否可能被复制、以及恢复路径有多容易被社会工程攻击**。

## 一个常见误解：passkey 不等于无密码

passkey 可以让登录**完全不需要密码**（passwordless），但它也可以作为第二因素存在（此时叫"多因素 passkey"，会要求用户先输入用户名，再触发 passkey。）两种用法都合规。

现实中的过渡期很长。多数服务会同时保留密码、TOTP、恢复码。**这不是设计缺陷，是迁移策略**——用户换设备、浏览器不支持、企业有旧系统，都得有兜底。

这也意味着一个安全现实：只要密码登录的通道还开着，攻击者就会去打那条路。迁移期里最重要的动作往往是**关掉旧的口子**，而不是加新的机制。

## 服务端需要注意的几件事

如果你要实现：

- **`rp.id` 一旦确定就不能改。** 它绑定在每条凭据里。改域名会导致所有已注册的 passkey 失效。
- **challenge 必须一次一用、随机、够长。** 这是防重放的唯一手段。
- **存 `credential ID` 和公钥，不存任何用户可猜的东西。**
- **检查 `origin`。** 有些库会替你检查，有些不会。自己确认。
- **用户可发现凭据**（resident key）意味着认证器里存了用户名等信息，能做"无需输入用户名的登录"。这很方便，但认证器容量有限（硬件密钥通常 25 个左右）。
- **保留一个不依赖 passkey 的恢复路径**，并且认真设计它。这是整个体系里最常见的漏洞点——你加固了正门，后门还是短信验证码。

## 为什么它比 SSH key 更"好用"

同样是密钥对签名，passkey 和 SSH key 的体验差别巨大，原因是**谁负责保管和选择**。

SSH key 的选择由你手动做：`ssh-add`、配置文件、`-i` 参数。规则散落在很多地方，你能把 key 搞错。

passkey 的选择由浏览器做：它知道当前域名，自动筛出匹配的凭据，弹一个原生界面。**规则被实现进了平台，而不是留在用户的习惯里。** 这是它能被普通用户使用的原因，也是"为什么同样的密码学，SSH 没有变成大众方案"的答案。

一句话：SSH key 是给管理员用的，passkey 是给所有人用的。技术内核一样，封装层决定了受众。

## 带走的三句

1. **抗钓鱼来自签名里绑定域名，加上浏览器强制匹配 rp.id。** 不是来自"更强的加密"。
2. **私钥在哪儿，安全等级就在哪儿。** 硬件密钥 > 同步 passkey，差别在可复制性和恢复路径。
3. **迁移期最大的风险是旧通道没关。** 加了 passkey 但密码还能登，等于没换锁。
