# 总地图

这一篇只做一件事：把你可能遇到的名字一次性排到正确的位置上，然后回答"到底有多少种"。后面的九篇分别展开这张图里的每一格。

## 先给结论

**互不相同的证明机制只有三种**：直接出示（bearer）、对挑战签名、一次性派生。你会碰到的名字有四十个上下，其中三十多个是这三种机制配上不同的**存放方式**和**授权范围**。

所以"二十多种"这个感觉是准确的，但它数的是**名字**，不是**机制**。名字之所以多，是因为同一个机制会为了不同的使用场景被重新包装一次，并换上一个新名字。

一个类比：刀只有"切"这一种功能，但厨房里有主厨刀、削皮刀、面包刀、剁骨刀、刨丝器。数量是真的，种类不假，但理解它们不需要二十个独立的原理，只需要知道哪把刀对应哪种切法。用错刀不会让你彻底懵，但会让你觉得"怎么又有一种刀"。

类比到此为止——真正的差别在于，厨刀你可以随便换着用，而凭据用错了是安全事故。

## 四个轴

| 轴 | 允许的取值 | 决定什么 |
|---|---|---|
| 材料 | 对称秘密 / 密钥对 | 泄露后的后果、能否被复制 |
| 出示 | 直接出示 / 签名 / 一次性派生 / 不需要出示（本地解锁） | 网络上跑的是什么 |
| 主体 | 人 / 设备 / 进程 | 能否加交互式因素 |
| 存放 | 大脑 / 密码管理器 / OS 钥匙串 / 硬件 / 服务端 / 无（临时签发） | 谁能替你用、丢了怎么办 |

同一份材料可以在不同轴上有不同取值，这就是重名的来源。举例：同一个 ed25519 密钥对，放在 `~/.ssh/id_ed25519` 就是 SSH key；放进 YubiKey 的 PIV 槽就是智能卡凭据；被 WebAuthn 封装、加一个 RP ID 和 credential ID，就叫 passkey。**材料没变，其它三个轴变了，名字就变了。**

## 完整清单

按"轴上的位置"分组，不按字母序。加粗的是你点名过的。

### A. 直接出示类（bearing the secret）

| 名字 | 材料 | 主体 | 特点 |
|---|---|---|---|
| 密码 / passphrase | 对称 | 人 | 熵最低，必须限速 |
| PIN | 对称 | 人 | 通常配合某个持有物使用，不单独成立 |
| **PAT（personal access token）** | 对称 | 人（代机器用） | 长期、跨设备、可限 scope |
| **API key** | 对称 | 进程 | 通常一对（key id + secret） |
| **OAuth access token** | 对称（多为不透明串） | 人委托给应用 | 短期、带 scope 和 audience |
| refresh token | 对称 | 同上 | 长效，用来换新的 access token |
| session ID / session cookie | 对称 | 浏览器 | 服务端有状态，可即时吊销 |
| JWT（作 access token 用时） | 对称签名或非对称签名 | — | 自包含，服务端可无状态校验 |
| **认证器 app 的 6 位码** | 对称（种子派生） | 人 | 见 D 组，严格说不是这一类 |
| magic link / 邮件验证码 | 对称 | 人 | 一次性 URL 或数字 |
| 恢复码 | 对称 | 人 | 一串一次性密码，兜底用 |
| 预签名 URL（如 S3） | 对称（HMAC） | 进程 | 把权限编码进 URL 本身 |
| capability URL | 对称 | 任何人 | "知道链接就等于有权限" |
| SSH 私钥的口令 | 对称 | 人 | 只保护本地文件，不上网络 |

这一组的共同点是：**网络上传输的就是凭据本身**。截获即等于持有。业内把这种语义叫 bearer token——持有即身份（RFC 6750 只规定了它怎么在 HTTP 里传，这个语义本身比 RFC 更老）。

### B. 挑战签名类（proving without revealing）

| 名字 | 材料 | 主体 | 备注 |
|---|---|---|---|
| **SSH key** | 密钥对 | 人/进程 | 服务端存公钥 |
| SSH 证书 | 密钥对 + CA 签名 | 人/进程 | 不用逐个登记公钥 |
| **GPG key** | 密钥对 | 人 | 主要在签名/加密，不是登录 |
| GPG 的 `[A]` 认证子密钥 | 密钥对 | 人 | 可当 SSH key 用 |
| **passkey** | 密钥对 | 人 | WebAuthn 封装，绑域名 |
| FIDO2 / U2F 硬件密钥 | 密钥对 | 人 | passkey 的物理形态之一 |
| TLS 客户端证书 / mTLS | 密钥对 | 人/进程 | 双向 TLS |
| 智能卡 / PIV | 密钥对 | 人 | 私钥在卡里，不出卡 |
| **TPM / Secure Enclave 中的密钥** | 密钥对 | 设备 | 私钥物理上不可导出 |
| 签名后的 git commit | 密钥对 | 人 | 证明"这次提交是我做的" |
| SPIFFE SVID | 密钥对（短期） | 进程 | 见第 10 篇 |
| Kerberos 票据 | **对称** | 人/进程 | 异类，见第 3 篇的对比 |

### C. 授权与委托类（不是认证，是"准许谁做什么"）

| 名字 | 它是什么 |
|---|---|
| OAuth 2.0 / 2.1 | 委托授权框架，不是认证协议 |
| OIDC | 建在 OAuth 2 上的身份层，给出 ID token |
| SAML 2.0 | 企业 SSO 的老方案，XML 断言 |
| scope / role / permission / policy | 权限的四种常见表达方式 |
| PKCE | 公共客户端的授权码保护（RFC 7636） |
| DPoP | 把 bearer token 变成"持有者受限"的 token（RFC 9449） |
| token exchange | 令牌换令牌，链式委托（RFC 8693） |
| SCIM | 用户和组的自动化同步，与认证无关 |

### D. 一次性派生类

| 名字 | 材料 | 备注 |
|---|---|---|
| HOTP | 对称种子 + 计数器 | RFC 4226 |
| **TOTP** | 对称种子 + 时间 | RFC 6238，认证器 app 里那个 6 位数 |
| 推送确认（number matching） | 非密码学 | 靠人确认，不是算法 |
| 邮件 / 短信验证码 | 对称 | 技术上同类，信道更弱 |

### E. 存放与基础设施层（本身不认证任何东西）

| 名字 | 它是什么 |
|---|---|
| **密码管理器** | 加密存一堆凭据，一个主密码解锁 |
| **Google 密码管理器 / 密钥保管箱** | 同上，且能存 passkey 和 TOTP 种子 |
| iCloud 钥匙串 | 同上，Apple 生态 |
| **KMS**（AWS KMS、GCP KMS、Azure Key Vault） | 服务端保管密钥，用 API 签/解，密钥不出服务 |
| HSM | 物理硬件版 KMS |
| **TPM** | 主板上的小芯片，绑机器 |
| Secure Enclave / Strongbox | 手机里的独立安全芯片 |
| **YubiKey** | 一根钥匙串，里面分了好几个互不相干的"槽" |
| ssh-agent / gpg-agent | 在内存里代你签名，免去反复输口令 |
| 操作系统钥匙串 | Windows Credential Manager、macOS Keychain、libsecret |
| Vault / SOPS / sealed-secrets | 集中管理服务端密钥 |
| 密码本 | 最原始的方案，熵很高，不可撤销 |

YubiKey 值得单独提醒一句：一根 YubiKey 里同时装了 FIDO2、PIV、OpenPGP、OATH 四套互不相干的功能。很多人以为"我买了 YubiKey 所以我有 passkey 了"，其实你只是买了一个**能装好几种机制的口袋**。这和上一篇文章里"认证器 app 是容器、passkey 是内容"是同一个错误。

### F. 你现在可能想问的漏项

你列表里没有、但确实是一类的：生物识别（指纹、人脸）、Kerberos、SAML、mTLS、SPIFFE、设备指纹、无密码登录链接、SSO、OIDC 联邦、工作负载身份。这些在第 5、6、7、10 篇里都有位置。

## 那么，一共多少种

按不同粒度数，你会得到三个不同的答案，三个都对：

| 数法 | 数量 | 什么时候有用 |
|---|---|---|
| 证明机制 | 3~4 | 想理解原理 |
| 材料 × 主体 × 出示方式 的组合 | 约 10 | 想做技术选型 |
| 有独立名字的方案 | 约 40 | 想读懂别人写的文档 |

你要的"到底有多少种"，多半是第三个答案。但真正能省下记忆的是第一个。

## 怎么用这张图

下次看到一个陌生名词，别去搜它是什么，先问：

1. 它在 A/B/C/D/E 哪一组？
2. 如果是 A/B/D，材料是对称还是密钥对？
3. 它保护的是人还是进程？
4. 它躺在哪一格存放层里？

四个答案出来，这个词的位置就定了，剩下的细节随时可以查。下一章从最底下那块砖开始：为什么"两种材料"这个说法能撑起整本书。
